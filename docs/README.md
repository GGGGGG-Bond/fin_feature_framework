# 文档入口与维护约定

文档与代码在同一仓库维护。最后整理：2026-10-14。当前完成版本管理及建设计划，功能迭代尚未开始。

## 阅读顺序与职责

| 文档 | 回答的问题 | 维护方式 |
|---|---|---|
| [原始需求](requirements.md) | 项目要解决什么、题目如何验收 | 原文保留；新增范围单独说明 |
| [当前进展与开发记录](progress.md) | 做到哪里、验证过什么、下一步是什么 | 每个交付批次更新状态并追加记录 |
| [建设计划](implementation-plan.md) | 后续分阶段建设与验收标准 | 范围或接口变化时修订 |
| [架构说明](architecture.md) | 当前已实现的模块与数据流 | 随实际架构变更更新；历史记录保留日期 |
| [设计决策](decisions.md) | 为什么选择某方案、替代方案与代价是什么 | 重要选择独立编号并记录状态 |
| [开发指南](development.md) | 怎么安装、运行、调试和维护 | 命令、配置与环境变化时更新 |
| [缺口与弱点](gaps-and-weaknesses.md) | 原始技术债分析 | 保留分析；实时状态链接到 progress |
| [协作约定](../AGENTS.md) | 两位 agent 如何分工与交接 | 协作规则改变时更新 |

## 写什么、何时写

开始一个批次：读取协作约定、当前进展和对应计划阶段；在 progress 中说明目标、范围、负责人和基准 commit。

完成一个批次：记录实际改动、验证命令、输入范围、结果、限制和待解决项；同步更新受影响的架构、使用说明与状态。文档随该批次代码一并提交。

需要改变数据口径、来源选择、版本模型、迁移方案或失败处理时：先在 decisions 中记录问题、备选方案、选择理由、后果和验证办法。设计者提出，审阅者确认；用户决定涉及业务范围、权限或采购的事项。

## 事实与状态

统一使用“待实施、进行中、待审阅、已验收、暂缓”。测试通过只能支持对应测试覆盖的结论，不能代替真实数据验收。“已验收”需要注明验收范围及证据；不能以合并或文档完成代替功能验收。

区分已经观测的事实、设计建议和待验证解释。发现旧记录不准确时，追加更正和依据，保留历史上下文，不把旧快照悄悄改成当前状态。设计决策采用“提议、已采纳、已否决、被替代”；采纳方案也不表示实现已经完成。

记录可审阅的设计依据、选择和权衡，不粘贴整段聊天或无关推演。重复内容通过链接引用：progress 是当前状态入口，plan 是目标与验收契约，decisions 是选择依据。

## 证据与仓库边界

命令记录工作目录、基准 commit、输入范围与结果。实际输出较大时只保存必要、经过检查的摘要或公开小样本；运行数据、数据库和详细日志仍在忽略目录中。

不记录密码、token、私钥、临时 JumpServer 账号或会话编号。Git 分支和 commit 作为交接依据；仓库是主要记录来源，本地导出的副本仅供查看。

阶段 1 将补齐财务数据字典与特征定义；在实现前明确契约，不将尚未编写的文档列为已完成。
