## DEC-001：代码与项目文档统一维护

日期：2026-10-14。提出/维护：架构与审阅 agent。采纳依据：用户选择个人私有 GitLab 仓库，并要求通过项目内文档记录开发过程和思考。

**问题**：聊天中的计划、验证与设计考虑难以随代码版本交接。原有说明书不能清楚反映当前状态或两位 agent 的开发进度。

**备选方案**：仅保存聊天；单独维护外部文档；在项目 Git 内维护 Markdown。

**决定与理由**：代码和文档同仓库保存。README 提供入口，progress 记录当前状态与批次事实，decisions 记录选择与代价，plan 维护目标及验收契约。沿用已有说明书，减少重复维护。

**后果**：每批代码变更需要同步受影响的文档；文档也参与审阅。仅把必要公开小样本作为 fixture，不把运行数据库、日志或凭据加入仓库。当前三类轻量文件足够，决策数量增加后再拆分 ADR。

**验证**：检查导航链接及引用文件；以 Git commit 串联代码、文档和验收记录。

## DEC-002：主来源采集、第二来源核验、公告抽查

日期：2026-10-14。状态：提议。提出：架构与审阅 agent；协作 agent 已评审范围，用户尚未确认功能执行。

**问题**：单一来源没有外部核验通道；直接增加接口也无法解决单位、版本和报表范围不一致。

**备选方案**：保持单源并只做内部规则；双源全量采集并混合填补；主源继续采集、第二来源做有限样本核验，差异追溯正式公告。

**建议与理由**：采用第三种方案。保留东方财富，优先探测新浪财务报表候选；不同封装库如果仍访问同一东方财富上游，不算新增独立来源。首轮核验 8 家公司、2 个年报期、6 个核心金额字段，先证明差异解释与证据追溯能力。

**代价与边界**：增加来源适配、口径转换和差异处理维护量。两来源一致不能单独证明正确，不自动平均或多数投票选值。第二来源不静默进入主结果。缺少真实冲突时使用标明构造的 fixture 检验冲突分支。

**待验证**：来源可用性、字段定义、日期与修订元信息、频率限制和真实样本差异。确认这些信息后再冻结映射与容差。参见 [建设计划](implementation-plan.md)。

## DEC-003：保留版本证据，限制历史查询承诺

日期：2026-10-14。状态：提议。提出：架构与审阅 agent；协作 agent 已提出时间与失效边界的修正。

**问题**：最新清洗值无法代表历史某天的可见值；来源可能只保留最新修订，公告日期也未必是该修订值的生效时间。

**备选方案**：只保留最新结果；用当前最新财报回填全部历史；保留已观察版本并对可信日期提供截至日查询。

**建议与理由**：采用第三种方案。分别保存报告期、公告/修订时间与观察时间，用内容变化记录新版本。查询区分市场公开时间和系统获取时间。修订日期未知时不沿用首次公告日回填；当前结果被替代后保留旧版输入和结果。

**代价与边界**：存储与查询更复杂，需要迁移和版本选择测试。不能恢复采集前已经丢失的历史版本；仅保证已保存、日期可信的版本查询。首轮采用日末语义，不增加盘中可用性或完整交易日历承诺。

**待验证**：实际来源版本字段可靠性、同日修订区分、数据迁移、未来修订隔离、依赖期重算和离线重放。阶段 1 仅先修正过滤与当前结果；阶段 2 留存版本；阶段 4 验收历史选择和传播。

## DEC-005：阶段 2A 数据模型与事务所有权

日期：2026-10-16。维护：实现 agent；经四轮独立审阅（R1-R7、A1-A6、B1）修订。采纳依据：MR!2 阶段 2 计划已合入 main，用户授权 2A 实现。

**问题**：阶段 1 仅做最小定义隔离，不建设版本存储、原始响应留存或血缘追溯。阶段 2A 需建立数据模型与迁移框架，但多轮实现存在事务所有权断裂、观察关联缺失、哈希不一致、证据校验不足等问题；第三轮复审进一步暴露嵌套事务、存量库边界、观察元信息、run 一致性和哈希边界缺口；第四轮复审暴露迁移当前投影与阶段一选值规则分歧。

**选择与理由**：

1. **事务所有权（R1）**：移除全部写入方法的 `with self.conn` 自动提交，新增 `unit_of_work()` 上下文管理器。理由：使多个写入可组合为原子单元，失败一起回滚；现有独立调用方用 `unit_of_work` 包装。备选（保留自动提交+显式 commit）会维护两套代码路径，正是被修复的 bug 根源。

2. **观察关联（R3）**：新增 `statement_observation` 关联表而非在 `statement_version` 上加列。理由：同一版本可被多次观察，每次关联不同 snapshot；单列 `snapshot_id` 只能记录首次。同内容重复观察不制造新版本，但通过关联表保存观察与 snapshot 的关系。

3. **统一标准化（R4-b）**：扩展 `standardize_record` 接受 `unit_map` 参数，迁移传入固定 `FIELD_UNITS`。理由：复用统一入口的有限数检查、布尔检查、未知单位处理，不维护两套标准化规则。备选（手写转换循环）跳过了 `math.isnan`/`math.isinf` 检查，导致 Infinity 进入标准字段与哈希。

4. **哈希内部计算（R6）**：Repository 内部调用 `hashing.py` 计算哈希，不接受调用方提供的值。理由：确保哈希与负载一致，杜绝"有效格式但负载矛盾"的静默去重。`canonical_json` 使用 `allow_nan=False` 禁止非有限值。

5. **证据一致性（R5）**：`evidence_sufficient=1` 时校验 snapshot 的 source/secucode/report 与版本一致。理由：有 snapshot 不等于证据一致；外键只证明 ID 存在，不证明快照支持这条版本。schema 默认 0 + CHECK 约束双重保障。

6. **嵌套事务所有权（A1）**：`unit_of_work` 最外层检查 `conn.in_transaction`，无外层事务时 `BEGIN` 自有事务；有外层事务（`with conn:` 或外层 `unit_of_work`）时使用独立 `SAVEPOINT`，内层成功只 `RELEASE`、失败只 `ROLLBACK TO` 自己的范围。理由：内层无条件 commit/rollback 会提交同一连接上的全部外层数据，使现有公开模块（增量/清洗/计算/质量）无法安全组合进外层事务。备选（拒绝嵌套）会限制组合能力。

7. **草稿库结构升级（A2）**：新增 v3 迁移幂等补齐旧 v2 草稿库缺失的表/列/索引。旧 `statement_version` 缺新哈希约束时，为空则重建、含数据则明确拒绝（提示从受支持阶段一副本迁移）。理由：迁移只看版本号会静默接受不完整结构，首次观察写入才报缺表；不能静默声称成功或删除原库数据。

8. **观察元信息（A3）**：`statement_observation` 加 `notice_date`/`revision_notice_date`/`revision_type` 列，保存每次观察的公告/修订元信息；`statement_version` 行保留首次披露。理由：同内容重复观察时后续修订元信息归属本次观察，不能在复用内容版本时丢弃，也不能更新版本行冒充最新披露。

9. **run 一致性（A4）**：`evidence_sufficient=1` 时除来源/公司/报表外，校验快照 run 与版本 run 一致；`save_raw_snapshot` 在创建边界校验 run 存在且来源一致。理由：两个外键分别存在不证明属于同一次捕获，按批次审计会相互矛盾。多采集输入的计算批次仍独立，不混为一谈。

10. **哈希边界（A5/A6）**：schema CHECK 改为 `NOT GLOB '*[^0-9a-f]*'` 全串校验（`GLOB '[0-9a-f]*'` 的 `*` 匹配任意后续字符，只约束首字符）；`normalize_numeric` 统一数值表示（整数值 float 转 int，如 `100.0`→`100`），存储与哈希共用同一结果。理由：schema 第二层校验须真正成立；Python/JSON 数值类型差异（`100` vs `100.0`）不应制造内容修订。

11. **投影复用阶段一选值规则（B1）**：迁移的当前投影改读完整旧来源元信息（`SELECT *`，含 `entry_time`），直接复用阶段一已验收的 `cleaning.dedup.sort_key`（`notice_date` → `entry_time` → 内容摘要），不再用 `COALESCE(notice_date, crawled_at)` 排序。理由：未知公告日的记录本不该凭采集时间取得公告优先级，两套排序会静默改变当前有效版本（复审给出两条反例：已知公告 120 被未知公告、采集更晚的 100 顶替；双方公告日未知时按采集先后而非 `entry_time` 选值）。并列歧义按既定内容摘要回退，并以 `dedup_ambiguous` 记入 `clean_log` 保留歧义。备选（在迁移里再写一套等价排序）会立刻产生第二次漂移。

**代价与边界**：所有写入方法的调用方需显式提交（用 `unit_of_work` 包装）；现有测试因同一连接内未提交写入可见而通过，跨连接测试需显式提交。R3/A3 观察关联与元信息为 2A 存储接口，历史查询留待阶段 4，文件落盘与真实采集留待 2B。A2 仅覆盖实际存在的草稿结构，不承诺升级任意未知库。A6 仅规范化整数值浮点，不转换会丢失允许精度的类型。B1 的投影含义限于"按阶段一规则选出当前版本 + 保留全部历史与歧义"，`observation_seq` 只是该规则下的排序位置，不声明已证实的公告/修订先后；不提供就已迁移库的就地重投影（B1 修正前阶段 2A 从未合入或发布，不存在持有旧投影的已发布库）。

**验证办法**：263 测试通过（含 59 项复审修复专项）；独立复现脚本 8/8 通过；B1 独立复现脚本显示两个反例旧投影=100、阶段一规则与修复后迁移=120；哈希可从存储字段重算；事务回滚不残留部分数据（含嵌套）；错来源/公司/表/批次的 snapshot 被拒绝；旧草稿库升级或明确拒绝；`100` 与 `100.0` 同一版本；迁移当前投影与阶段一 `deduplicate` 结果逐组一致、每组当前唯一、历史 1:1 保留、重跑幂等。

## DEC-006：2B 采集证据与单元事务

日期：2026-10-16。提出/维护：架构与审阅 agent。状态：已采纳为实现契约；不表示功能验收。基准 main c9da710。用户要求契约到位后开工；[执行契约](stage-2/2b-contract.md)及其 schema/矩阵为交接依据。

**问题**：现有 fetch_all 丢弃页信封，失败/重试 body 无留存路径；2A 接口未接生产采集；两条 CLI 在水位、批次、异常退出上分叉。仅增加 JSON 文件不能解决尝试身份、双介质一致性与行级血缘。

**选择与理由**：attempt 是每页真实 HTTP 调用序号；保存 Response.content 原字节，不用重序列化 JSON 替代证据。每 run 分别存文件，unit/page/attempt 唯一，不做跨批次内容寻址。文件先不覆盖发布，审计独立提交；失败业务 UOW 回滚但文件和尝试保留，依靠只读对账识别孤儿。2B 就写版本/观察和来源行下标，2C 再切清洗。两个 CLI 共用财务协调器，crawl 股票发现也留存。合法空可成功，零计划失败，部分失败非零退出。水位以完整单元共同提交为门禁，run 最终状态由单元汇总，解除旧概要循环约束。

**备选及权衡**：只存成功 JSON 维护简单但丢失败原体；把 attempt 定为跨批次重跑无法表达同页 HTTP 重试。全局内容寻址可省磁盘，但增加引用/GC 协调成本，本批不取。失败自动删文件可能毁掉崩溃调查证据且难保证删对；本批保留并对账。SQLite/文件不能真实同事务，不声称双介质原子性。

**代价与边界**：v4 增加 unit/attempt 表、快照元信息与观察定位；请求 observer、文件校验、股票发现接线和故障注入工作量增加。失败数据会占磁盘，后续 GC/恢复须另立契约。旧充分性标记不伪装为真实原体证据；旧版本首次元信息保留，新观察表达新证据。只做 eastmoney 获准小样本；不含 2C/2D、双源或生产操作。

**验证**：[46 组验收场景](stage-2/2b-test-matrix.md)要求原字节一致、同身份冲突、每次响应/无响应尝试、崩溃孤儿、事务回滚、分页完整、行观察、迁移与两条 CLI 状态。文档 DDL 校验只证明规范可执行，不替代实现回归与独立审阅。

### 2B-1 实施记录（实现 agent，2026-10-16；状态：待独立审阅）

在 DEC-006 已采纳的契约内，实现方对契约未逐条指定之处做了以下选择，供审阅与后续批次复用：

1. **v4 不并入 `ALL_DDL`**：v4 对象单独迁移，空库的 v1 基线不提前创建 2B 结构；版本 ≥4 时每次 `run_migrations` 复查必需表/列/索引，只有版本号不足以跳过结构检查。
2. **升级入口先备份**：`migrate_with_backup` 对"已有版本记录或已有数据"的库先用 SQLite backup API 写唯一新副本（含 WAL 已提交内容）再迁移，备份失败即不迁移；显式目标已存在直接拒绝，自动命名保证不覆盖。删掉迁移"就地重试等于一次成功"的不确定性只靠事务回滚保证（DDL/加列/索引/版本登记同事务）。
3. **`save_raw_snapshot` 两条路径**：带 `attempt_id` 的新证据路径必须校验真实文件（存在/大小/哈希）并逐项核对 unit/run/source/report/company/page；无 `attempt_id` 的 legacy 路径只能落 `legacy-unverified` + `legacy_unverified`，且不能被改判为 v4 结论。
4. **单元完整性用可注入证明**：`UnitEvidence`（complete + 全部最终页 snapshot + `row_verifier`）代替"必须先提交 unit.success"的循环依赖；`row_verifier` 由协调器提供并在 Repository 内被调用，因此"row_index 能重建本次映射/标准值"是可核验条件而非调用方声明。
5. **来源行身份预检先于投影变更**：`(snapshot_id,row_index)` 的重放幂等与矛盾冲突在修改 `is_superseded`/`superseded_by` 与观察行之前判定，冲突时当前投影与既有观察都不残留部分改动。
6. **对账严格只读**：`audit-raw` 不执行迁移、不建表、不删除孤儿或临时文件、不补抓；未结算 attempt 在**任何**单元状态下都报 `unfinished_attempt`（不只成功单元），`transport_error` 允许无快照。
7. **路径段白名单**：仅接受来源名 `[a-z][a-z0-9_]*`、UUID/摘要 `[A-Za-z0-9_-]{1,64}`、正整数页/尝试号；公司名、`report_name`、用户输入绝不作为路径段。

**代价与边界**：失败时的孤儿文件与临时文件会占用磁盘且不自动清理（GC/恢复须另立契约）；`UnitEvidence` 的强度取决于协调器提供的核验器，2B-2 必须由协调器真实重建；本批未接 HTTP、未升级任何真实数据库，`audit-raw` 尚无真实库可对账。

**验证办法**：`tests/test_raw_store.py`、`tests/test_ingestion_migration.py`、`tests/test_ingestion_unit.py`、`tests/test_raw_audit.py` 共 91 项，配合既有回归共 343 项离线通过；故障分支均为真实注入（fsync/link/DB 插入/迁移中途/备份目标/损坏 gzip）。B01-B15 与 B42 的场景到用例映射见 [2B 验收矩阵](stage-2/2b-test-matrix.md)。

### 2B-1 审阅整改记录（实现 agent，2026-10-17；状态：待复审）

独立审阅对送审头 `b8b2b3f` 提出 4 项 P1 + 4 项 P2（R1-R8），整改选择如下（审阅材料：分支 `docs/review-stage2b1-b8b2b3f`，commit `8857ecc`）：

1. **R1 备份入口下沉到 `init_schema`**：常规建库入口也走"有待执行迁移且库已有数据则先备份"路径，不只 `migrate_with_backup`。理由：`init_schema` 是 CLI/测试默认入口，若它绕过备份，含历史数据的 v3 库会被直接升级 v4 而无副本。
2. **R2 只读连接与只读 RawStore 分离**：新增 `get_readonly_connection`（`mode=ro`，不创建库/目录、不改 `journal_mode`）与 `build_readonly_raw_store`（`readonly=True`，根不存在即拒绝）。理由：`audit-raw` 的只读承诺不能依赖调用方自觉，须在连接与存储两层强制。
3. **R3 孤儿判断用全库引用集合**：按 run 过滤对账时，孤儿基准仍是全库所有快照引用的文件，仅文件扫描范围限定到所选 run 的目录前缀。理由：按 run 过滤引用集合会把其他批次的合法文件误报为孤儿。
4. **R4 来源行身份预检增版本分组与诊断**：`(snapshot_id,row_index)` 幂等比对除内容哈希与四项元信息外，还比 `report_date`/`table_type`/`source_name`/`secucode`（版本分组）与 `normalization_diagnostics`。理由：同一行定位改传另一报告期或不同诊断，静默返回原期间版本等于丢失修订。
5. **R5 备份目标用私有临时 + `os.link` 原子不覆盖**：先写唯一私有临时文件，再 `os.link` 发布；`FileExistsError` 即并发抢先拒绝，失败清理只删自己的临时文件。理由：`exists()` 检查与 `connect(target)` 之间存在竞争窗口，并发可覆盖刚生成的其他备份。
6. **R6 v4 结构复查增必需列**：`collect_v4_structure_gaps` 除表名与部分列外，还逐列校验 `ingest_unit`/`ingest_attempt` 的必需列。理由：删掉 `error_code` 等列后版本号仍为 4，结构不完整却被接受。
7. **R7 单元完整性逐页重核当前文件**：`_verify_unit_evidence` 不只信历史 `valid` 标志，逐页重新核对当前文件存在且哈希/大小一致。理由：完整性证明中的另一页文件已删除，仍能新增 `evidence_sufficient=1` 版本。
8. **R8 成功单元全部最终页必须 valid**：`_check_unit_evidence` 检查每页最终尝试（同页最大 `http_attempt`）必须 `valid`；`attempt_without_snapshot` 只对最终尝试报告。理由：成功单元仍有 pending 页，对账却返回干净、退出 0。

**非阻断 H1（2B-2 前须修）**：`create_statement_version` 两处 `_record_observation` 未传 `observed_at`，观察时间落到 `datetime(now,localtime)` 而非实际接收 UTC——2B-2 接 HTTP 时一并修。

**验证办法**：全量离线 369 项通过（原 343 + R1-R8 整改回归 26 项）；反例脚本 R1/R2/R3/R4/R6/R7/R8 均按预期抛错，R5 反例为假阳性（monkeypatch 不触发，已用直接探针验证真实竞争被阻断）。

### 2B-1 复审整改记录（实现 agent，2026-10-17；状态：待复审）

复审对送审头 `e3d03f7` 确认 R1-R8 全部关闭，但扩展检查发现 1 项 P1 + 3 项 P2（C1-C4），整改选择如下（审阅材料：分支 `docs/review-stage2b1-e3d03f7`，commit `5550052`）：

1. **C1 结构核验覆盖全部运行写入列与索引定义**：`V4_INGEST_UNIT_REQUIRED_COLUMNS` 补 `started_at`/`ended_at`/`failure_code`/`detail`；新增 `V4_REQUIRED_INDEX_SPECS` 与 `_index_definition`，`collect_v4_structure_gaps` 逐索引查 unique 标志、列集与部分条件。理由：R6 只补了举出的一个字段，同名非唯一索引冒充唯一索引也未识别；结构核验应在初始化时报清楚缺口，而非在采集途中失败或丢失约束。
2. **C2 终态失败响应不能凭 valid 标志冒充充分证据**：`_verify_unit_evidence` 与 `_check_unit_evidence` 都检查最终尝试 `outcome=ok` 且 HTTP 2xx；http_error 等终态失败即使文件有效、快照标 valid 也拒绝/报告。理由：原文件有效不代表这是成功响应；矛盾数据必须在此拒绝，不只指望协调器不生成。
3. **C3 成功财务单元核对声明页数与连续页号**：`_check_unit_evidence` 解析每页原体信封（pages/count），核对各页声明总页数一致、页号从 1 连续、合计行数等于声明 count；缺页报 `missing_declared_page`。理由：`final_by_page` 仅由已有 attempt 构造，不知道声明页数，缺中间页/尾页仍报干净。
4. **C4 区分"最终页成功完整"与"每次收到响应留证据"**：`_check_attempts` 对非最终 http_error/business_error/decode_error/schema_error/storage_error 缺快照报 `failed_response_without_evidence`；transport_error 可无 snapshot。理由：R8 改动对所有非最终尝试直接 continue，把收到 HTTP 4xx/5xx 但未留原体的证据丢失也静默豁免；契约允许历史失败重试页 invalid，但收到响应必须留证据。
